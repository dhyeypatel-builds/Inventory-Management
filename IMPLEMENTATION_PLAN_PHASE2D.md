> **How to use this document:** Each task has **Objective · Files · Acceptance · Testing**. Task IDs (`PR-02`) are stable references.

---

## 1. Shape

- The existing [`ReportResult`](backend/src/modules/reports/reports.service.ts) abstraction already separates **data** from **rendering**. This phase is almost entirely **new renderers** over the same `ReportResult` — low blast radius. The six reports' data queries change only insofar as 2A U-03 already added tenant scoping.
- **Branded PDF via HTML → headless Chrome.** Drop hand-drawn PDFKit primitives for an HTML+CSS template printed by the same `puppeteer-core` + Chrome already used in `frontend/scripts/shoot.mjs`. Far easier to make genuinely good; trivially supports charts and per-tenant branding.
- **Ops note (must resolve in PR-01):** the **backend** container does not currently ship Chrome — only the frontend tooling does. The backend Dockerfile must install Chromium (or use a Chrome base image), and the renderer must **launch one browser instance and reuse it** (a pool), never spawn per request.

---

## 2. Dependencies

- `exceljs` (XLSX). `puppeteer-core` already present. Chart.js loaded in the report HTML page (no server canvas needed — Chrome renders it).
- Backend image: add Chromium + required fonts (incl. a font with the £ glyph and tabular figures to match the app).

## 3. Development Tasks

### EPIC PR — Branded PDF pipeline

#### PR-01 · HTML→PDF rendering service + browser pool
- **Objective:** A service that renders an HTML string to PDF via a long-lived headless Chrome instance (launch once, reuse; health-check + relaunch on crash). Backend Dockerfile gains Chromium + fonts.
- **Files create:** `backend/src/render/pdf.service.ts`, `backend/src/render/browser-pool.ts`.
- **Files modify:** `backend/Dockerfile` (Chromium + fonts), `backend/src/config/env.ts` (Chrome path), package deps.
- **Acceptance:** Given HTML, returns a valid PDF buffer; the browser is reused across calls; a crashed browser auto-relaunches; concurrent requests are serialized/pooled safely.
- **Testing:** Integration: render a known HTML → non-empty valid PDF; concurrency test (N parallel renders succeed); kill-and-recover test.

#### PR-02 · Branded report HTML template
- **Objective:** A reusable HTML+CSS report template: header band with **tenant logo + shop name + VAT number** (from settings/storage), report title, period, generated timestamp; a styled table with zebra rows, right-aligned £/number formatting (`en-GB`, tabular figures), a summary block (cards or bold totals), and a footer with page numbers + "Generated by TyreStock". Print-CSS paged correctly.
- **Files create:** `backend/src/modules/reports/templates/report.html.ts` (template fn taking `ReportResult` + tenant branding).
- **Acceptance:** Renders any of the six reports with correct branding, formatting, and pagination; long tables page cleanly with repeated headers; empty report shows a graceful "no data" state.
- **Testing:** Integration: render each report type; snapshot key HTML; visual check of the produced PDF.

#### PR-03 · Charts in the report
- **Objective:** Embed a chart where it adds meaning: sales report → trend line; best-selling-brands → bar; stock-valuation → bar. Chart.js in the HTML page, fed from `ReportResult.rows`, printed by Chrome.
- **Files modify:** the PR-02 template (conditional chart block per report `name`).
- **Acceptance:** Applicable reports show an on-brand chart above the table; chart matches the table data; non-charted reports render unchanged.
- **Testing:** Integration: charted reports contain the chart in the PDF; data parity with the table.

#### PR-04 · Wire reports to the new renderer
- **Objective:** Route `format=pdf` through PR-01/PR-02/PR-03; retire `writeReportToPdf` (PDFKit) or keep it behind a feature flag as a fallback.
- **Files modify:** `backend/src/modules/reports/reports.controller.ts`, `reports.routes.ts`.
- **Acceptance:** Every report's PDF download uses the branded renderer in the caller's tenant context (branding = that tenant); old endpoint contract preserved.
- **Testing:** Supertest: each report `?format=pdf` returns a branded PDF; two tenants get their own branding; isolation holds (2A U-03).

### EPIC XL — Excel export

#### XL-01 · `reportToXlsx(report)`
- **Objective:** A generic XLSX renderer mirroring the existing `reportToCsv`: typed columns (currency/number/date), a bold/totaled summary row from `report.summary`, frozen header row, sensible column widths, sheet named per report.
- **Files modify:** `backend/src/modules/reports/reports.service.ts` (add alongside `reportToCsv`); add `exceljs`.
- **Acceptance:** Produces a valid `.xlsx` opening cleanly in Excel/LibreOffice/Sheets; numbers are real numeric cells (not text); £ formatted; totals present.
- **Testing:** Unit: generate a workbook from a fixture `ReportResult`; assert cell types, header freeze, totals.

#### XL-02 · `format=xlsx` endpoint
- **Objective:** Content negotiation: `?format=json|csv|xlsx|pdf` with correct content-type and filename; permission-gated; tenant-scoped.
- **Files modify:** `reports.controller.ts`, `reports.routes.ts`.
- **Acceptance:** `?format=xlsx` downloads a correctly-named workbook with the right mime; unknown format → 400.
- **Testing:** Supertest: xlsx content-type + disposition; bad format rejected.

### EPIC RF — Reports frontend

#### RF-01 · Export menu + states
- **Objective:** Replace any single download button with an export menu (PDF / Excel / CSV), with loading + error states (PDF/XLSX are async server renders).
- **Files modify:** `frontend/src/features/reports/pages/ReportsPage.tsx` (+ components).
- **Acceptance:** Each format downloads with a spinner during generation and a clear error on failure; keyboard-accessible menu.
- **Testing:** RTL: each option hits the right endpoint with the active filters; loading/error rendered.

#### RF-02 · In-app report preview polish
- **Objective:** Bring the on-screen report table up to the Light Industrial bar (number-is-the-hero typography, aligned £ columns, summary emphasis) so the preview matches the exported PDF.
- **Files modify:** report table components.
- **Acceptance:** On-screen report visually consistent with the PDF; responsive; accessible table semantics.
- **Testing:** RTL renders; design pass with the `impeccable` skill.

---

## 4. Definition of Done (Phase 2D)
- Every report exports as a branded PDF (tenant logo/name/VAT), an Excel workbook, and CSV.
- Applicable reports include an on-brand chart in the PDF.
- The backend renders PDFs via a reused headless-Chrome instance shipped in its image; no per-request browser spawn.
- Exports are tenant-scoped and branded per tenant; isolation (2A) holds.
- The in-app report preview matches the exported output.

## 5. Out of scope for 2D
- Scheduled/emailed reports (deferred; would build on 2C email infra).
- Custom report builder / ad-hoc queries.
- Cross-tenant analytics for the master admin (a 2B platform-reporting follow-up).
